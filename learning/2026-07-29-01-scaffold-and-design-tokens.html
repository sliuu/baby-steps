Worth noticing

The template already used the exact pattern this whole step is built on: a :root block of variables, an @theme inline block turning them into Tailwind utilities, and a media query swapping the values for dark. We did not invent this structure — we grew it from two colors to about forty.

4 · Intuition

One name, two values

A theme switcher is tempting to build the naive way: write both colors everywhere and pick between them. 

<!-- The trap -->
<div class="bg-white text-black dark:bg-black dark:text-white">
<div class="bg-white text-black dark:bg-black dark:text-white">
<div class="bg-white text-black dark:bg-black dark:text-white">

Every element now knows about both themes. Adding a third, or nudging the cream a shade warmer, means editing every file. Instead, elements name a role, and the theme decides what that role looks like:

1 · The value
:root {
  --surface: #fdfcf8;
}

.dark {
  --surface: #221f1b;
}
→
2 · The bridge
@theme inline {
  --color-surface:
    var(--surface);
}
→
3 · The class
<div class="bg-surface">

Step 2 is the part that's specific to Tailwind v4. Naming a variable --color-surface inside @theme is what makes bg-surface, text-surface and border-surface exist as classes. The inline keyword means "keep the var() reference rather than resolving it now" — which is exactly what lets the same class produce different colors under .dark.

The markup never changes. Only the value at the top of the chain does:

Light — <html>
class="bg-surface"
resolves to
#fdfcf8
⇄
Dark — <html class="dark">
class="bg-surface"
resolves to
#221f1b
Key concept — design token

A named decision, stored once. --ink-muted is a token; #8a8378 is not. Tokens name the role ("muted text") rather than the appearance ("greyish brown"), so a redesign is an edit in one file rather than a search across the codebase.

Why shadcn is not a component library

Installing a normal component library puts its code in node_modules/. You import from it and configure it through whatever props the author decided to expose. If you want a Button with a different focus ring and the author didn't add a prop for it, you're stuck overriding CSS from outside.

npx shadcn add button does something different: it writes a 67-line components/ui/button.tsx into your repo, which you then own and edit like anything else you wrote. There is no Button in node_modules.

But we didn't need to edit it. The file it wrote already refers to roles, not colors: 

default: "bg-primary text-primary-foreground hover:bg-primary/80"

So pointing --primary at our warm near-black was enough. Same component, same file, untouched:

Before — as the CLI wrote it

Geist sans · neutral grey

After — our tokens reached it

EB Garamond · warm near-black

Why this matters later

Step 9 needs a modal with a focus trap; Step 10 needs a form. Those are hard to get right and boring to write. shadcn hands us a correct starting point that already speaks our token vocabulary — and when the default look is wrong for us, we edit the file instead of fighting it.

The flash of the wrong theme

The theme lives in localStorage, which only exists in the browser. The server renders HTML without it. So the obvious implementation — read the preference in a React effect — produces a visible white flash on every load for a dark-theme user:

HTML arrives
paints LIGHT
JS loads
React hydrates
effect → DARK

Without the script — roughly 200–600ms of the wrong theme, every load.

HTML arrives
inline script sets .dark
paints DARK
React hydrates

With it — the class is on <html> before the first paint.

The fix is a small <script> in <head> with no async or defer. The browser stops, runs it, and only then paints. Blocking scripts are normally something to avoid; this is the standard exception, because the alternative is a visible defect.

Two kinds of numerals

A detail from the prototype worth naming, because we will lean on it repeatedly. Serif faces ship two sets of digits, and they are good at opposite jobs.

StyleLooks likeGood forBad at
Oldstyle
.oldstyle		 Digits rise and fall like lowercase letters — the 3 and 7 have descenders. Dates and running prose. "July 2026" sits in the line instead of shouting. Columns — the digits have different widths, so numbers won't align.
Tabular
.tabular		 All digits the same height and the same width. The Trends table. Counts stay put instead of jittering as they change. Prose — reads mechanically, and the even spacing looks gappy.

A · The type — app/layout.tsx

next/font/google is called at module scope, not inside the component. That is deliberate: it runs at build time, downloads the font files, and self-hosts them. Each call returns an object whose .variable is a generated class name that defines a CSS custom property. 

const cormorant = Cormorant({
  variable: "--font-cormorant",
  subsets: ["latin"],
  weight: ["400", "500", "600", "700"],
  display: "swap",
});

const ebGaramond = EB_Garamond({
  variable: "--font-eb-garamond",
  subsets: ["latin"],
  weight: ["400", "500", "600"],
  style: ["normal", "italic"],
  display: "swap",
});

Both class names go on <html>, so --font-cormorant and --font-eb-garamond are readable from anywhere in the document. subsets: ["latin"] ships only Latin glyphs — a meaningful size saving. 

<html
  lang="en"
  suppressHydrationWarning
  className={`${cormorant.variable} ${ebGaramond.variable} h-full antialiased`}
>
  <head>
    <script dangerouslySetInnerHTML={{ __html: THEME_INIT_SCRIPT }} />
  </head>
Edge case — suppressHydrationWarning

Our script adds class="dark" to <html> before React runs. React then compares the server's HTML against the browser's DOM, finds an attribute it didn't put there, and warns. This prop says "on this one element, that mismatch is expected." It applies only to <html>, not to descendants — it is not a general-purpose silencer.

dangerouslySetInnerHTML is React's deliberately alarming name for injecting raw HTML. The danger is injecting user input; this is a constant string we wrote.

B · The tokens — app/globals.css

Three blocks, in order. First the bridge that creates the utility classes:

@theme inline {
  --font-sans:    var(--font-eb-garamond), Georgia, serif;
  --font-heading: var(--font-cormorant), Georgia, serif;

  /* shadcn's contract — its components read only these names. */
  --color-background: var(--background);
  --color-primary:    var(--primary);
  /* …16 more… */

  /* Ours — the vocabulary the rest of Baby Steps speaks. */
  --color-surface:   var(--surface);
  --color-ink:       var(--ink);
  --color-ink-muted: var(--ink-muted);
  --color-hairline:  var(--hairline);

  --color-area-spirituality: var(--area-spirituality);
  --color-area-exercise:     var(--area-exercise);
  /* …four more areas, five moods… */
}

The split matters. The first group is a contract: shadcn components reference bg-primary and border-border, so those names must exist and must be sensible. The second group is ours, and nothing outside our code depends on it.

Then the values, twice:

:root {
  --bg:      #f7f4ed;   /* warm cream */
  --surface: #fdfcf8;
  --ink:     #1c1a17;   /* warm near-black, not #000 */
  --ink-muted: #8a8378;
  --hairline:  #e3ded2;

  --area-spirituality: #c4483c;   /* terracotta */
  --area-exercise:     #3178b5;   /* steel blue */
  --area-work:         #d9762b;   /* burnt orange */
  --area-creativity:   #ddb63c;   /* mustard */
  --area-romance:      #4c8b4a;   /* moss */
  --area-friends:      #9457c0;   /* amethyst */

  /* Moods reuse the same five hues, deliberately. */
  --mood-great: var(--area-exercise);
  --mood-good:  var(--area-romance);
  --mood-okay:  var(--area-creativity);
  --mood-low:   var(--area-work);
  --mood-rough: var(--area-spirituality);

  /* shadcn's names, pointed at ours. */
  --background: var(--bg);
  --primary:    #221f1a;
  --border:     var(--hairline);
  /* … */
}

.dark {
  --bg:      #1a1815;   /* warm charcoal, not blue-black */
  --ink:     #f0ebe0;
  --area-spirituality: #d75f52;   /* every hue lifted ~12% */
  --area-exercise:     #4a93ce;
  /* … */
}
Why the dark hues aren't the same hex

A color legible on cream is not automatically legible on charcoal. Contrast is a relationship between two colors, not a property of one. Each area hue is lifted in lightness for dark so a sticker stays readable in both.

Note also that --mood-* is defined in :root only. Because it points at var(--area-*) and CSS variables resolve at use time, the dark overrides flow through automatically — five aliases we never have to maintain twice.

Then the two figure utilities, using Tailwind v4's @utility directive:

@utility tabular {
  font-variant-numeric: tabular-nums lining-nums;
}

@utility oldstyle {
  font-variant-numeric: oldstyle-nums proportional-nums;
}

And the base layer, which sets body type and the graph paper:

@layer base {
  html { @apply font-sans; }        /* EB Garamond everywhere by default */

  body {
    @apply bg-background text-foreground;
    background-image:
      repeating-linear-gradient(to right,  var(--grid-line) 0 1px, transparent 1px 28px),
      repeating-linear-gradient(to bottom, var(--grid-line) 0 1px, transparent 1px 28px);
  }

  h1, h2, h3 { @apply font-heading; }   /* Cormorant for display */
}

The grid is two 1px gradients crossed at 28px, in a colour that is 4% opaque. No image file, and it re-tints itself per theme because --grid-line is a token like any other.

C · The theme — lib/theme.ts and components/ThemeToggle.tsx

The script that runs before paint:

export const THEME_INIT_SCRIPT = `(function () {
  try {
    var stored = localStorage.getItem("baby-steps-theme");
    var theme =
      stored === "light" || stored === "dark"
        ? stored
        : window.matchMedia("(prefers-color-scheme: dark)").matches
          ? "dark"
          : "light";
    document.documentElement.classList.toggle("dark", theme === "dark");
    document.documentElement.dataset.theme = theme;
  } catch (e) {}
})();`;

An explicit choice wins; otherwise we follow the operating system. The try/catch is not defensive noise — localStorage throws outright in Safari private mode, and an uncaught error in a blocking head script would stop the page.

The toggle is our first Client Component:

"use client";

export function ThemeToggle() {
  const [theme, setTheme] = useState<Theme>("light");
  const [ready, setReady] = useState(false);

  useEffect(() => {
    setTheme(document.documentElement.classList.contains("dark") ? "dark" : "light");
    setReady(true);
  }, []);

  function toggle() {
    const next: Theme = theme === "dark" ? "light" : "dark";
    setTheme(next);
    document.documentElement.classList.toggle("dark", next === "dark");
    localStorage.setItem(THEME_STORAGE_KEY, next);
  }
  // …renders Sun or Moon, nothing until `ready`
}
Key concept — Server and Client Components

In the App Router every component is a Server Component by default: it runs once on the server, and its JavaScript is never sent to the browser. That is the right default — most UI is static.

"use client" opts a file into being a Client Component, which ships to the browser and may use state, effects, and event handlers. A toggle needs all three. The rule of thumb: anything with useState, useEffect, or onClick needs the directive.

The ready flag deserves a word. The DOM already knows the theme, but React renders on the server first, where there is no DOM to ask. So the component starts at a placeholder value and corrects itself in an effect — and renders no icon at all until it has. Showing a sun for one frame in dark mode would be a worse bug than showing nothing.
