The Shell

A top bar that switches between two pages without the browser ever navigating — and the line between code that runs on the server and code that gets sent to your laptop.

The whole step in five lines

  1. We built a top bar: wordmark, two tabs, moon icon, avatar.
  2. Clicking a tab swaps the page body. No reload, no URL change.
  3. One value — page — decides which tab is filled and what shows below.
  4. That value lives in AppShell, because two components need it.
  5. The calendar and trends views stay on the server. We proved it with grep.

2 · Tools — and every word I use

Nothing below is defined later than it is used. If a word here shows up in §3 or §4 and you've lost it, this is the section to jump back to.

React words

component A function that returns a description of some UI. TopNav is one. You use it by writing <TopNav />.
props The values you pass into a component — its arguments. <TopNav page="calendar" /> passes a prop named page.
state A value a component remembers between renders. Props come from outside; state is the component's own.
render React calling your component function to find out what should be on screen. A re-render is it calling again because something changed.
hook A function whose name starts with use, which plugs a component into a React feature. useState is the only one this step.

Browser words

DOM Document Object Model — the browser's live tree of the elements on the page. You don't edit it directly here. React does.
event Something that happened: a click, a keypress, a form submit.
event handler A function that runs when an event happens. onClick={...} registers one.
bundle / chunk The JavaScript files shipped to the browser. A chunk is one such file. Smaller bundle = the page becomes clickable sooner.
hydration The browser attaching event handlers to HTML the server already sent. Before it, the page looks right but doesn't respond.

Next.js words

Server Component The default. Runs on the server, sends finished HTML, ships zero JavaScript to the browser.
Client Component A file marked "use client". Runs on the server and in the browser, so it can hold state and handle clicks.
directive A bare string at the very top of a file that changes how the file is treated. "use client" is one.
static The HTML was built once, during npm run build. Loading the page does no server work. Marked ○ in the build output.

Syntax you'll see below

JSX HTML-looking syntax written inside JavaScript. <TopNav /> is not HTML — it compiles to a function call.
fragment <>...</>. Groups several elements without adding a wrapper to the page.
ternary test ? a : b. A one-line if/else that produces a value. Reads as "if test, then a, otherwise b."
union type A type listing the exact allowed values: "calendar" | "trends" means those two strings and nothing else.
ARIA Extra HTML attributes that tell screen readers what something means when the visual design alone can't.

New this step, specifically

ThingWhat it doesWhy we need it
useState Gives a component a value that survives re-renders, plus a function to change it. Changing it triggers a re-render. Holds which page is showing. One line instead of a router.
"use client" Marks where server-only rendering stops and browser JavaScript begins. State and clicks only exist in a browser. Two of our six new files need it.
preventDefault() Cancels the browser's built-in response to an event — here, following a link. Lets the tabs be real <a> elements with no page load.
Lifting state up When two components need the same value, it lives in their nearest shared parent and travels down as props. The nav and the body both need to know the active page.
aria-current Announces "this is the one you're on." A filled pill means nothing to a screen reader. This is the part that isn't decoration.

3 · Intuition

Four ideas: what it looks like, why links, where state lives, server vs client.

What we built

Baby Steps Calendar Trends ☾ ◍
the page body swaps here — nothing else moves

Wordmark left. Two tabs centred. Moon and avatar right. One hairline underneath.

Click Trends and only the area below the bar changes. The URL stays put. The back button stays grey. Nothing reloads.

Why the tabs are links, not buttons

A tab that swaps content in place could be a <button>. We used <a href>. Two reasons:

  • Keyboard and screen-reader users already know what a link in a nav bar does.
  • Steps 5–15 may give these views real URLs. The hrefs are already written. Only the click handler would change.

The cost is one line — we have to cancel what the browser wants to do:

onClick={(event) => {
  event.preventDefault();   // don't follow the href
  props.onPageChange(id);   // do this instead
}}
What preventDefault actually prevents

Every event has a built-in browser behaviour: a link navigates, a form submits, a checkbox toggles, the spacebar scrolls. preventDefault() switches that behaviour off for this one event.

It does not stop the event travelling up to other handlers. That is stopPropagation() — a different method for a different problem. We want the first one.

Where the state lives

Two components need to know which page is active:

  • The nav, to decide which pill is filled.
  • The body, to decide what to show.

React's answer is not to give each one a copy. It's to put the value in their nearest shared parent and pass it down. That parent is AppShell.

AppShell · client
const [page, setPage] = useState("calendar")
→
TopNav · client
page → which pill onPageChange → setPage
→
the body
page === "calendar" ? calendar : trends

TopNav owns nothing. It receives the current page and a function to call, and it has no idea what that function does. So it can be restyled or reused without touching the logic, and the logic can move without touching the markup.

Server and client

Every component runs on the server by default and sends only finished HTML. "use client" opts a file into also running in the browser. Its JavaScript gets downloaded, and React reattaches the event handlers to the HTML that's already painted. That reattaching is hydration.

server renders
HTML paints
client JS arrives
hydration

You can read the page at step 2. You can click it at step 4. Keeping the bundle small shortens the gap.

The test for whether a file needs the directive: does it use state, an effect, or an event handler? Here that's three files — AppShell (state), TopNav (clicks), and ThemeToggle (all three, from Step 1). Everything else stays on the server.

The directive spreads downward, through imports

Once a file says "use client", everything it imports joins the client bundle too.

That's the trap. Import <CalendarView> into AppShell and the whole calendar ships to the browser — even before you've clicked anything.

The way out: this applies to imports, not to props. A Server Component passed into a Client Component is rendered on the server and handed over as finished output. So app/page.tsx stays a Server Component, builds both views, and passes them down: 

<AppShell calendar={<CalendarView />} trends={<TrendsView />} />

The shell knows how to switch between two unknown things. It never learns that they're a calendar and a chart, and it never imports them. §5 is the proof this worked.

app/page.tsx · server
renders CalendarView and TrendsView here
→
AppShell · client
receives them as props, picks one
→
browser
gets the switcher's JS, not the views' JS

4 · Code

Five files, smallest first.

House style — how to read a component signature

Every component below looks like this: 

type Props = { … };

export function Thing(props: Props) { … }

There is exactly one parameter, named props, and it's an object. React always calls a component with one argument — the object holding everything you passed in JSX. So <Thing a={1} b={2} /> becomes Thing({ a: 1, b: 2 }).

The : Props after it is a type annotation, the same colon as in const n: string. It is required — strict is on in our tsconfig.json, so an un-annotated parameter fails the build. Its real payoff is at the call site: forget a prop in app/page.tsx and you get an error there, instead of a silently blank half-page.

We keep the props. prefix rather than destructuring to { calendar, trends }. It costs seven characters per use and buys one thing: you can always tell at a glance that a value came from outside the component, not from a line above.

lib/nav.ts — the shared vocabulary

export type Page = "calendar" | "trends";

export const PAGES: { id: Page; label: string; href: string }[] = [
  { id: "calendar", label: "Calendar", href: "#calendar" },
  { id: "trends",   label: "Trends",   href: "#trends"   },
];

Plain data. No "use client", no React. A server file and a client file can both import it, because it contains nothing that needs either environment.

Page is a union type — those two strings and nothing else. TypeScript now rejects setPage("calender") at build time.

It lives here rather than in AppShell.tsx to avoid a circular import (two files each importing the other). The shell renders the nav; if the type lived in the shell, the nav would have to import back into it.

components/AppShell.tsx — the state

"use client";

import { useState } from "react";
import { TopNav } from "./TopNav";
import type { Page } from "@/lib/nav";

type Props = {
  calendar: React.ReactNode;
  trends: React.ReactNode;
};

export function AppShell(props: Props) {
  const [page, setPage] = useState<Page>("calendar");

  return (
    <>
      <TopNav page={page} onPageChange={setPage} />
      <main className="mx-auto w-full max-w-5xl flex-1 px-8 py-14">
        {page === "calendar" ? props.calendar : props.trends}
      </main>
    </>
  );
}

Three things to notice:

  • useState<Page>("calendar") returns a pair: the current value, and a function to change it. Calling setPage("trends") tells React this component is out of date. React re-runs the function, gets different JSX, and updates the DOM to match. Nothing in our code says "hide the calendar" — we describe what the page looks like for a given state, and React works out the difference.
  • React.ReactNode is the type meaning "anything renderable": elements, strings, arrays, null. It's what lets the shell accept two views it knows nothing about.
  • The fragment <>...</> keeps the header and <main> as siblings, which is what Step 1's layout expects.

components/TopNav.tsx — the bar

Three regions in a row. The middle one takes all leftover space and centres its contents, which is what keeps the pills centred on the page rather than centred between their neighbours. 

<header className="sticky top-0 z-20 border-b border-hairline
                   bg-background/85 backdrop-blur-sm">
  <nav className="mx-auto flex h-16 w-full max-w-5xl items-center gap-6 px-8">
    <span className="font-heading text-2xl font-semibold tracking-tight">
      Baby Steps
    </span>

    <div className="flex flex-1 justify-center"> … pills … </div>

    <div className="flex items-center gap-1">
      <ThemeToggle />
      <span aria-hidden className="grid size-9 place-items-center
                                   rounded-full bg-secondary text-ink-muted">
        <User className="size-[17px]" strokeWidth={1.5} />
      </span>
    </div>
  </nav>
</header>

bg-background/85 is Step 1's colour token at 85% opacity — the /85 suffix works on any colour utility. Combined with backdrop-blur-sm, content scrolling underneath is blurred rather than hidden. Because --background already has a different value per theme, this needs no dark-mode variant.

Each pill:

{PAGES.map(({ id, label, href }) => {
  const active = id === props.page;
  return (
    <a
      key={id}
      href={href}
      aria-current={active ? "page" : undefined}
      onClick={(event) => {
        event.preventDefault();
        props.onPageChange(id);
      }}
      className={`rounded-full px-5 py-1.5 text-[0.95rem] transition-colors ${
        active
          ? "bg-secondary text-ink"
          : "text-ink-muted hover:text-ink"
      }`}
    >
      {label}
    </a>
  );
})}
  • key={id} is required on anything produced by .map(). React uses it to match elements between renders instead of rebuilding the whole list.
  • aria-current is undefined when inactive, not false. undefined removes the attribute; aria-current="false" would be a claim rather than an absence.
Both class names are written out in full — on purpose

Step 1 established that Tailwind finds classes by scanning your source as plain text. It never runs your code. So bg-secondary and text-ink-muted must each appear literally somewhere, or the CSS for them is never generated.

The tidier-looking {`bg-${active ? "secondary" : "transparent"}`} compiles, runs, and renders an unstyled pill. No error. No warning. Write complete class names on both branches.

5 · Verifying it

The important claim is invisible in the browser, so we check it with grep.

The claim: the views really did stay on the server. The build writes the browser's JavaScript into .next/static/chunks/. If the calendar's text is in there, it shipped. 

$ grep -rl "The month goes here" .next/static/chunks/
(nothing)

$ grep -rl "Trends" .next/static/chunks/
.next/static/chunks/29i6nal-6xuxx.js

Both results matter, in opposite directions:

  • Absent: the calendar's text is in no client chunk. It exists only in the prebuilt HTML. That's the win.
  • Present: the word "Trends" is there, because lib/nav.ts is imported by TopNav, which is a Client Component. The tab label had to travel. That's the boundary, made visible.

By hand

  • Click Trends — the body changes, the URL bar doesn't.
  • Press Tab — the wordmark is skipped, both pills take focus with a visible ring, then the moon.
  • Toggle the theme while on Trends — you stay on Trends. Theme and page are separate state.
  • Reload — you land on Calendar. The page choice isn't saved anywhere, by design.
  • Narrow the window — the three regions hold until roughly phone width. Desktop-first was the brief.
Known and accepted

Back and forward do nothing, and you can't send someone a link to Trends. Both follow from "no browser navigation," which the spec asked for. The hrefs are in place if that changes.
