2 · Words you'll need

migrationOne .sql file, applied once, in filename order. Never edited after it ships — you write a new one instead.
RLSRow-Level Security. A rule attached to a table that Postgres silently adds to every query against it.
policyOne RLS rule, for one operation. using filters rows you may see; with check validates rows you write.
constraintA rule the table refuses to break — unique, check, not null. Rejects bad writes rather than correcting them.
triggerA function the database runs automatically when a row changes.
upsertInsert, or overwrite if it's already there. One request, no "does it exist?" check first.

3 · What this changes for you

Four things. The SQL underneath them is in the box at the end.

1 · Rules you'd normally write in the UI now live in the table

"A day holds any number of stickers, but only one mood" is one line of schema: 

unique (user_id, day)

So dropping a mood onto an occupied day isn't a branch you write. It's an upsert — insert, or overwrite the one that's there — and the database decides which. No "does this day already have a mood?" round trip, no race between two fast drops, no state to keep in sync.

You'll feel this in Step 8, when drag-and-drop lands: the drop handler stays a single call, and the interesting work is all animation.

2 · Queries don't filter by user, and mustn't start to

await supabase.from("life_areas").select("…").order("sort_order");
// no .eq("user_id", …) anywhere

RLS adds where user_id = auth.uid() inside Postgres, on every query, whether or not the caller remembered. Adding the filter in the app too would work — and would suggest the safety lives in the query file. Then one forgotten line becomes a leak.

Practical effect: you can write a component that fetches whatever it needs without first checking who's asking. The wrong rows aren't hard to reach — they're unreachable.

3 · color_key is a hue, and an area is a row

Step 1 named the colour tokens after the six areas. That's now inverted: the hue is the real value, and the area name is an alias. 

--ramp-red: #c4483c;                      /* the value */
--area-spirituality: var(--ramp-red);     /* an alias */

A life area is a database row holding color_key: 'red'. So the seventh area someone adds in v2 picks an existing ramp — no CSS edit, no chart edit, no new token. That was the whole reason the plan said "names a ramp, never a hex."

The Tailwind trap, second sighting

bg-ramp-${colorKey} produces nothing. Tailwind finds class names by scanning source text, so a name assembled at runtime never makes it into the compiled CSS. lib/palette.ts writes all six out by hand for exactly this reason.

Same shape as Step 3's process.env.NEXT_PUBLIC_…. Worth recognising as a category: build-time tools read your file, they don't run it.

4 · The data arrives before the HTML does

export async function CalendarView() {
  const areas = await getLifeAreas();
  …
}

A Server Component can be async and just await the database. No loading state, no skeleton, no useEffect, and no Supabase client in the browser bundle for this query. The browser receives finished markup with the chips already in it.

When you do want a skeleton — for something genuinely slow — that's a <Suspense> boundary around the component, not state inside it. Nothing here is slow enough to need one yet.

4 · Code

Four snippets. Read the line under each only if the code looks odd.

RLS is two steps, and the second one alone is the dangerous case

alter table life_areas enable row level security;   -- deny everything

create policy "read own life areas" on life_areas
  for select to authenticated
  using ((select auth.uid()) = user_id);           -- allow this much back

Enabling without policies locks everyone out — loud and obvious. Writing policies without enabling does nothing at all, and the app keeps working perfectly while the table sits wide open. If you ever audit this project, that's the thing to check first.

(select auth.uid()) — the parentheses aren't decoration. Wrapped in a select, Postgres evaluates it once per query instead of once per row.

life_areas has no insert or delete policy

create policy "read own life areas"   … for select …
create policy "update own life areas" … for update …
-- and that's it

You can read your six and rename them. You cannot add or remove one, because no policy permits it. "Editing life areas is a v2 feature" stops being a thing we remember and becomes a thing the database enforces.

The seed trigger runs as the owner, not as you

create function public.seed_life_areas(for_user uuid)
  … security definer
      set search_path = ''

security definer runs the function as its owner, so it can insert rows for a user who has no session yet and couldn't pass the RLS check themselves. search_path = '' is the safety catch that has to come with it — it stops a planted schema shadowing a table name inside a function with elevated rights. That's why every name in the file is written public.something.

Foreign keys carry user_id along

foreign key (activity_id, user_id)
  references activities (id, user_id) on delete restrict

A plain references activities(id) would let a row point at an activity belonging to someone else — RLS filters what you can read, not what you can reference. Pairing the columns makes that impossible.

on delete restrict, not cascade: deleting a life area must never quietly delete months of history. Retiring one is what the archived flag is for.

5 · Verifying it

The RLS check, without a browser:

$ curl "$URL/rest/v1/life_areas?select=id,name" -H "apikey: $ANON_KEY"
[]

Empty array, not an error. That's the shape of a working policy: the rows exist, the request was valid, and Postgres filtered every one of them away because there's no session. A 401 would mean something else was stopping it — and would still be true if RLS were off.

Then, signed in:

npx supabase migration list   # local and remote match, all three
npm run build                 # / still ƒ dynamic, /login still ○ static

Six chips under "Your life areas" on the Calendar page, in spec order.

Worth doing once, by hand

Open the Supabase dashboard → Table Editor → life_areas. You'll see your six rows. Then look at the same table through the SQL editor while signed out of the app — the rows are still there. RLS doesn't hide data from the owner of the database; it filters what an application request can reach. Knowing which is which will save you an hour someday.
