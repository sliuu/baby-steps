The Month Grid

Forty-two cells, always. Plus the reason a calendar is the one component that can't trust the clock.

The whole step in five lines

  1. The grid always draws six rows, so its height never changes between months.
  2. Days are "2026-08-12" strings, never Date objects, everywhere outside lib/dates.ts.
  3. The server doesn't know what day it is where you are, so "today" appears a beat after first paint.
  4. Today is a ring, not a filled circle — a fill needs inverted text, and inverted text broke once already.

2 · Words you'll need

hydrationThe browser re-running a component over HTML the server already sent, to attach the interactivity. The two runs must produce identical markup.
derived stateA value recomputed from another value instead of stored beside it. The 42 cells are derived from the month.
timezoneAn offset from UTC. Your server is almost certainly on UTC; you are not. For about seven hours a day they disagree about the date.
DSTDaylight saving. Two days a year are 23 or 25 hours long, which breaks anything that advances a date by adding 86,400 seconds.
oldstyle figuresNumerals that rise and fall like lowercase letters. Set in the date numbers so they sit in the page rather than shouting from it.

3 · What this changes for you

Four things you'll design around. The mechanics are in the box at the end.

1 · The grid never changes height

Six rows always, even when five would do. A 31-day month starting on a Friday genuinely needs six, and a grid that grows a row between August and September makes the whole page jump every time an arrow is pressed — the tray moves, the footer moves, and the eye loses its place mid-scan.

So the extra row is a design decision, not a maths accident. February gets a row of greyed-out March, and that's the price of a page that holds still.

2 · "Today" isn't in the first paint

The HTML is built on a server in UTC. It has no idea what date it is in your kitchen. So the first frame the browser draws has no today marker, and the ring appears a moment later once the browser can answer.

That constrains the marker: it must not change the cell's size or position, or the whole grid twitches on load. A ring drawn inside the numeral's own box is safe. A larger cell, a border on the cell, or bold text that reflows the row is not.

The alternative — reading the clock during render — produces a hydration mismatch: React builds the markup twice, gets two different answers, and warns in the console. See §4.

3 · Today is a ring, because a fill needs inverted text

The first version was a filled ink circle with the numeral knocked out in the page background colour. The number vanished — one missing token and "light text" resolved to nothing, leaving dark ink on a dark circle.

A ring never has that failure mode. The numeral keeps the same colour it already had; the ring is added around it. Nothing about legibility depends on a second token being correct.

Build-time tools read text, third sighting

The actual bug: text-bg was a class Tailwind had never heard of, because --color-bg was missing from the @theme block. An unknown utility isn't an error — it's just nothing. The rule that keeps catching us: if a token isn't published in @theme, its class silently does nothing.

Same family as Step 3's process.env.NEXT_PUBLIC_… and Step 4's bg-ramp-${key}.

4 · Every cell already has a handle

<div data-day="2026-08-12" …>

Nothing reads it yet. Step 8 will: a drop target needs an identifier that survives the trip from DOM event back to database row, and "2026-08-12" is exactly what day_activities.day stores. Same string, no conversion at either end.

The hairlines between cells, incidentally, aren't borders. The grid has a 1px gap and a coloured background showing through it — one rule instead of per-cell borders that double up at every seam.

4 · Code

Three snippets. The first is the one worth remembering.

The clock, on both sides of hydration

const todayString = useSyncExternalStore(
  noSubscription,
  () => today(),   // browser: the visitor's own date
  () => null,      // server AND hydration: we don't know yet
);

The third argument is the trick. React uses it on the server and for the hydration pass, then immediately switches to the second. So both runs agree on null, the markup matches, and the real date arrives one render later.

Reach for this any time a component needs something only the browser knows — the current time, localStorage, the actual theme class, matchMedia. ThemeToggle has the identical shape for the identical reason.

Not useEffect + setState. That works, but React's set-state-in-effect lint rule rejects it, and it renders the wrong value once before correcting.

toISOString().slice(0, 10) is wrong a third of the day

format(date, "yyyy-MM-dd")           // local calendar fields  ✅
date.toISOString().slice(0, 10)      // converts to UTC first  ❌

At 11pm on the 12th in California, UTC is already the 13th. A sticker placed at night would land on tomorrow. date-fns' format reads the local fields and never converts.

The same reasoning is why addDays and addMonths do the stepping rather than arithmetic on timestamps — two days a year aren't 24 hours long.

Two classes for one slot is a coin flip

function numeralClasses(cell: DayCellData): string {
  if (cell.isToday) return "font-medium text-ink ring-1 ring-ink";
  if (cell.inMonth) return "text-ink";
  return "text-ink-muted/60";
}

If text-ink and text-ink-muted both land on an element, Tailwind picks the winner by position in the compiled stylesheet — not by the order you wrote them in the template. Writing the later one second changes nothing. Branches that return exactly one class per slot are the fix.

5 · Verifying it

Date bugs are seasonal — the February one shows up in February. So the checks are a script rather than a browser pass: 

$ npm run check:dates
TZ = America/Los_Angeles
PASS  weekday labels start on Sunday
PASS  42 cells
PASS  first cell is 2026-06-28
…
PASS  late-night stays on its own day
      toISOString would have said: 2026-08-13
…                                            18 lines, no FAIL

$ TZ=Pacific/Auckland npm run check:dates     # the same 18

Among them:

  • July 2026 matches the reference screenshot cell for cell.
  • February still draws six rows.
  • Exactly one cell is today — and zero when the clock is unknown.
  • 11:30pm resolves to the right day. The script prints what toISOString would have said, for contrast.
  • Stepping across a DST boundary and across a year boundary both land correctly.

No test runner. It's a .mts file Node runs directly, throwing on failure. A real one arrives when there's something worth mocking.

Worth doing once, by hand

Run TZ=Pacific/Kiritimati npm run dev and load the page. Kiritimati is UTC+14 — reliably a different date from your machine. Watch the today ring: nothing on the first frame, then it appears. That flash is the hydration boundary, made visible.

6 · What's next

Step 6 — stickers that are already in the database appear on their days.

The Server Component fetches rows, then reshapes the flat list into a Map<"2026-08-12", Sticker[]> so each cell does one instant lookup instead of scanning the whole month. The data-day string from this step is the map key.

Nothing about the grid changes. That's the point of having spent a step on it alone.

Concepts from this step that come back: derived, never stored · useSyncExternalStore for browser-only values · days are strings · one class per slot · data-day as the drop key.
